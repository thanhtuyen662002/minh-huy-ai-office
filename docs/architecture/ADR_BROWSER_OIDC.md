# Browser OIDC sign-in

Issue260 / Draft261 implements the product browser Authorization Code/S256 PKCE flow. This document records an active implementation, not completed browser or production acceptance.

## Trusted configuration and login transactions

`apps/web/lib/browser-oidc.ts` obtains public app origin, exact issuer, authorization/token/JWKS endpoints, client identity and transaction key exclusively from operator environment configuration. An invalid enabled configuration fails generically. Deployed endpoints require HTTPS. Explicit local HTTP mode requires a loopback app and browser identity; the only additional HTTP backchannel host is the fixed `identity:8080` local service. Request Host/forwarded headers never choose a callback or provider endpoint. The callback is fixed at `/api/local/session/oidc/callback`.

Configuration names are `AIOFFICE_BROWSER_OIDC_ENABLED`, `AIOFFICE_BROWSER_OIDC_PUBLIC_ORIGIN`, `AIOFFICE_BROWSER_OIDC_ISSUER`, `AIOFFICE_BROWSER_OIDC_AUTHORIZATION_ENDPOINT`, `AIOFFICE_BROWSER_OIDC_TOKEN_ENDPOINT`, `AIOFFICE_BROWSER_OIDC_JWKS_URI`, `AIOFFICE_BROWSER_OIDC_CLIENT_ID`, `AIOFFICE_BROWSER_OIDC_CLIENT_SECRET` (optional for a PKCE public client), `AIOFFICE_BROWSER_OIDC_TRANSACTION_KEY` (canonical base64url encoded32 random bytes), and `AIOFFICE_BROWSER_OIDC_LOCAL_HTTP` (local disposable/installed loopback use only). Raw origins have no trailing slash; issuer/endpoints are canonical absolute URLs without credentials/query/fragment. No production credentials are tracked here.

Every transaction creates independent256-bit random state, nonce and verifier, binds a canonical requested company and expires after300 seconds. AES-256-GCM authenticates and encrypts these values. HKDF separates the transaction encryption context by exact issuer/client/fixed callback; ciphertext cannot move between application/issuer/client configurations. The serialized cookie is bounded to2048 characters; malformed encodings, tampering, unknown fields, unsafe timestamps, extended lifetime or expired cookies fail closed. A10-second maximum future issuance allowance handles bounded server clock skew. Production transaction cookies use the `__Host-` name with Secure/HttpOnly/SameSite=Lax and Path=/; the route must enforce those properties when it is added.

The transaction is short-lived authentication coordination. It carries no platform task state, user/tenant authority or roles. The API must resolve fresh company/user/role authority after verified token exchange and before a session is issued. Stateless transaction cookies require a stable shared private transaction key across BFF instances; a key change invalidates only pending logins.

## Private code exchange adapter

`browser-oidc-client.ts` pins `openid-client`6.8.8. Authorization requests use Code/S256, fresh state/nonce and the fixed callback. Token exchange requires exact expected state/nonce/verifier and an ID token, explicitly enables `enableNonRepudiationChecks`, restricts ID-token signatures toRS256 and verifies configured issuer/audience/lifetime. It refuses ambiguous state/code or an unpinned callback before provider fetch. Provider requests retain a10-second deadline/no-store and reject redirects; actual response bodies are bounded to65536 bytes irrespective of Content-Length. Signed ID subject and access-token subject must agree; Core still must verify the access signature/issuer/API audience/lifetime and resolve fresh roles. Session lifetime cannot exceed provider expiry, signed token expiry or3600 seconds. Exceptions become generic errors without raw provider details.

## Consumption, revocation and concurrency contract

Encrypted transaction cookies alone are reusable within their TTL. `browser-session-store.ts` now implements private shared Redis coordination using pinned node-redis6.3.0. Each browser binding has independent random256-bit identity and generation. Registration always creates a fresh identity; a missing/expired binding cannot be recreated from a presented old cookie. The binding cookie and opaque SID cookie must be HttpOnly/Secure/SameSite=Lax/Path=/ with `__Host-` names in HTTPS mode. Before start, the browser must already hold a registered binding; start and logout compare-and-swap its current generation. Callback never overwrites the binding cookie. Reordered older generation/SID cookies can lose availability but cannot regain authority.

Start advances the generation and supersedes pending callbacks while preserving the current active SID. Thus a denied new sign-in retains the issued session with the current binding. Atomic claim accepts one callback; completion checks the still-current generation/state/claim and unexpired transaction after fresh API authority. Completion stores one provisional encrypted replacement. Its first authenticated/decrypted read proves the browser received the new opaque SID; a second atomic generation/payload/expiry acknowledgment promotes it and removes the previous active SID. Concurrent acknowledgment is idempotent. A committed completion with a lost reply, expired or tampered replacement cannot evict the previous active session. Start discards an unobserved replacement; logout rotates the generation and deletes active/provisional/pending authority. Replacement rows also bind their publication generation, so a previous worker's logout/start that does not know the expanded fields cannot expose them after rotating the generation. Every BFF read compares current generation/SID before obtaining private access data. All scripts declare exactly one hashed browser key and use Redis TIME for deadlines. Keys/rows contain digests of handles/state, never a verifier or raw cookie authority. The short-lived access-token/session payload is AES-256-GCM encrypted with purpose-separated HKDF and binding/SID/configuration AAD; SQL retains durable platform task state.

Redis records also bind the Redis INFO server `run_id`, read atomically on every operation. Rows restored from a prior process fail closed. A required disposable CI test saves an active RDB, logs out, restarts only its CI Redis without saving the logout, verifies that the older active row was physically restored, and requires denial plus fresh-login recovery. This qualifies standalone process restart; arbitrary asynchronous HA promotion/rollback topology still requires separate proof and session invalidation before use. Production `AIOFFICE_BROWSER_SESSION_REDIS_URL` requires TLS (`rediss:`); explicit local mode permits loopback or fixed `redis:6379`. Authentication/HELLO and EVAL replies each have an explicit2-second hard deadline; offline queuing/reconnect replay is disabled. A real stalled TCP handshake initially exceeded the library connect timeout. Independent frozen19a12c2 review also reproduced acknowledged HELLO/CLIENT followed by an unanswered EVAL still pending beyond3500ms: node-redis removes its command timeout when a command leaves the write queue. Both waits now destroy the stalled connection on the application deadline. Separate real TCP tests prove HELLO stall and exactly one unanswered EVAL denial within3500ms, with socket cleanup. Errors never reflect endpoints/credentials/payloads and no process-local authority fallback exists.

## Registered start and callback routes

POST `/api/local/session/oidc/binding` requires the exact trusted same Origin before cookie/store access and prepares only a server-generated registered binding. A current binding is preserved without cookie rewrites. POST `/api/local/session/oidc/start` requires settled preparation and a strict JSON object containing only the canonical company ID, bounded to2048 actual UTF8 bytes and a10-second body deadline. Atomic start advances the binding generation before returning a pinned Code/S256 authorization URL and encrypted transaction cookie. Browser JSON contains no company/verifier/token/secret authority.

GET callback requires the exact raw configured Host, fixed path, bounded query, authenticated unexpired transaction and unambiguous matching state/code/optional issuer before the one-use shared claim. The request's internal origin or forwarded headers never choose the redirect or provider/Core endpoints. The callback uses the captured runtime Core origin, verifies signed tokens and fresh company authority, then atomically completes the still-current generation/claim. Success redirects only to the configured app root, writes the opaque HttpOnly SID and clears the transaction. Callback never writes a binding cookie, so delayed responses cannot restore a generation superseded by logout/new login. ## Private browser BFF and logout

Business routes have a browser-or-explicit-local gate; password grant retains its separate explicit local gate. Browser mode always reads opaque binding/SID authority from shared Redis and never falls back to a legacy access-token cookie, including configuration/store failure. The selected company must match the issued session's GUID value. BFF calls pin the captured Core origin, replace caller auth/company headers with private server-owned values, require no-store/no-redirect and a10-second deadline, and preserve caller cancellation. Core independently validates the signed access token and current membership/roles for every request. The BFF consumes the entire Core body with an8MiB actual-byte bound and the original deadline/cancellation signal before its final shared read and response publication. Large collections require pagination rather than an unbounded proxy response. This fence discards private replies whose session was revoked/expired during either headers or streamed-body processing. Source/task/connection-test mutations require configured exact Origin and raw Host before consuming a body or accessing cookies/upstreams. These checks also work after TLS terminates before Next.js, ignoring forwarded authority.

Browser logout requires a known registered binding and successful shared CAS revocation before rotating its cookie and clearing SID/transaction/legacy cookies. A stale generation returns409, an outage503; neither mutates cookies or claims logout success. Logout revokes BFF active/provisional/pending authority; provider JWT/global SSO revocation is not claimed. Unknown replies after committed start/logout generation CAS can lose availability because the browser still holds an old generation; relaxing that fence could restore revoked authority and is deliberately forbidden. Recovery uses a new registered binding/login.
