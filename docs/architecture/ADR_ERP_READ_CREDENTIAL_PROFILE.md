# Effective credentials for ERP reads

Issue #264 / PR #265, under full product #233. The frozen implementation passed actual owned SQL controls and independent security/runtime review. [Validation evidence](../validation/ERP_READ_CREDENTIAL_PROFILE.md) records the supported scope and exact runs; final PR/main delivery status is maintained in the PR HANDOFF.

Source `AllowRead` is platform policy. Successfully opening a connection establishes connectivity. Neither proves the SQL identity is unable to mutate persistent ERP data. Every independent ERP read session therefore runs `ErpReadOnlyConnectionVerifier` using its actual open connection and current security context. It accepts only an explicit integer proof, bounds its command timeout, preserves cancellation and returns a fixed nonsecret denial. Qualification is never cached by connection string, source, prior probe or pool.

The initial supported profile uses ad-hoc reads on standalone SQL Server 2022 (engine major16, `IsHadrEnabled=0`) with full server `VIEW ANY DEFINITION` and current-database `VIEW DEFINITION` metadata visibility. Other engine versions and availability-group ownership require a separately reviewed qualification. A filtered availability-group catalog is not proof of absent ownership. These are metadata permissions; they do not replace read permission on selected data. Effective server/database/schema/object rights must fit a conservative read/metadata allowlist. Impersonation, role administration, ownership, persistent DML/DDL and column UPDATE rights are denied. Missing/hidden metadata or unsupported results fail closed. Private SQL diagnostics and definitions are never returned by the proof.

Grant-option state is refused across every effective database/server token. Explicit database grants outside database/object/column/schema classes are refused, including TYPE or principal CONTROL/ALTER; server grants outside SERVER are refused except ordinary CONNECT on a verified TSQL endpoint. Public endpoint connectivity is not permission to administer it. Fixed database/server roles other than public are refused; a metadata-only fixed server role can still administer its membership. Custom nested read roles remain eligible only when all effective-right, token and ownership checks pass. Subordinate ownership is checked separately because it implies CONTROL without a permission row.

The database-scoped-credential catalog may be filtered; its supplemental visible-CONTROL check does not establish full visibility. The engine16 profile independently refuses class32 explicit grants/grant-options and database CONTROL/db_owner. Creating this credential requires database CONTROL, and credential ownership cannot be transferred through ALTER AUTHORIZATION. Owned runtime controls separately test the actual class32 grant and rolled-back DROP.

This profile refuses user functions, including functions reachable through views or computed expressions, and synonyms hiding external targets. Executable procedures or modules accessible to the reader are denied. External database/server, unresolved, caller-dependent or ambiguous dependencies are refused. Encrypted views, external tables, user CLR assemblies/types and linked servers are outside this profile. Views containing OPENQUERY/OPENROWSET/OPENDATASOURCE are conservatively refused, including textual false positives; dependency catalogs alone do not prove those facilities safe. This is a credential qualification for this current database and supported graph, not a claim of read-only access across the whole SQL instance. Supporting a legacy inventory function requires a separate reviewed dependency graph and versioned capability profile. This checkpoint does not declare Medcom/Novo's inventory functions qualified, and it does not register customer business adapters. The private customer mapping remains outside public Git.

Catalog evidence, typed capability execution and schema discovery require a proof before querying and another after the reader is disposed, before evidence is returned. A permission change during materialization discards the result. The read-only worker probe also explicitly requests qualification. Credential denial is an authorization failure in the worker and prevents a success checkpoint or provider call.

Trusted capability definitions additionally pass the pinned Microsoft ScriptDom parser in SQL160 mode before any connection is opened. Exactly one SELECT, optionally with CTEs, is accepted. Database/server-qualified object or function names, NEXT VALUE FOR, and external rowset facilities are refused. Persisted dependency metadata cannot qualify those ad-hoc references. Literal strings containing dotted names and normal local aliases remain supported. Parser errors return fixed nonsecret profile guidance, without SQL or parser diagnostics. This is a bounded qualification for the current profile, not a general SQL firewall for arbitrary user queries.

Read-only source connection tests request this profile from fresh server-owned source flags and reject policy changes while resolving/probing. Write-enabled source tests retain connectivity-only semantics. Legacy probe implementations cannot silently satisfy the new read-only request. API results and the browser provide bounded instructions to configure a dedicated read-only credential and appropriate metadata access without displaying upstream diagnostics.

Owned bootstrap grants the sample reader's metadata permissions and direct database SELECT only when initially creating the login/user. Direct SELECT avoids inheriting control of the fixed reader role's schema. Repeating bootstrap does not repair or re-grant revoked permissions. Existing configurations must be explicitly qualified by their operator; no customer privileges are changed by this implementation. Metadata DENY for any effective database principal also fails the profile, because an object-level DENY can hide a module despite a database metadata grant.

Permission semantics were checked against primary documentation: [effective permissions](https://learn.microsoft.com/en-us/sql/relational-databases/system-functions/sys-fn-my-permissions-transact-sql), [metadata visibility](https://learn.microsoft.com/en-us/sql/relational-databases/security/metadata-visibility-configuration), [column GRANT versus table DENY](https://learn.microsoft.com/en-us/sql/t-sql/statements/deny-object-permissions-transact-sql), [module execution/ownership chaining](https://learn.microsoft.com/en-us/sql/t-sql/statements/execute-as-clause-transact-sql), [database permissions and grant-option states](https://learn.microsoft.com/en-us/sql/relational-databases/system-catalog-views/sys-database-permissions-transact-sql), [server roles](https://learn.microsoft.com/en-us/sql/relational-databases/security/authentication-access/server-level-roles?view=sql-server-ver16) and [dependency boundaries](https://learn.microsoft.com/en-us/sql/relational-databases/system-catalog-views/sys-sql-expression-dependencies-transact-sql).

Definition of done includes actual owned SQL positive/negative controls, change-between-sessions and mid-read discard evidence, independent frozen security review, exact PR/main gates and durable HANDOFF. The frozen implementation has passed the runtime and review requirements; subsequent delivery hashes still require their own gates. Customer read-only credentials, schema/version qualification, inventory and stock-movement reconciliation, production deployment and full #233 remain incomplete.
