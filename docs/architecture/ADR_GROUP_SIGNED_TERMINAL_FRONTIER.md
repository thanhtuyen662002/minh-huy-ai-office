# Signed terminal frontier — issue 278 / Draft 288

Status: accepted direction for implementation; only the metadata integrity primitive is prepared in this checkpoint. Schema, SQL advance store, historical graph reader, current-authority key fences, worker DI and native qualification are not implemented by it.

## Problems to resolve

The existing mutable cursor's last terminal batch does not authenticate the completed prefix. A genuine receipt for `(2,4]` cannot prove that `(0,2]` completed. A malformed cursor pointing to that genuine receipt could otherwise skip pending work.

Requiring today's identical source/brain fingerprints to advance an already committed terminal can also lose progress: the process can crash after terminal commit, followed by a legitimate edit, recall or credential/grant rotation. The immutable old completion cannot be replaced. New terminal creation must retain its full current fences; advancement of an existing genuine completion is historical bookkeeping with separate fresh Extract authorization.

## Decision

Implement an append-only, signed advance chain. Each advance binds the exact source scope, sequential previous/current version, interval, terminal batch/operation/manifest hash, previous signed-envelope fingerprint, original terminal commit UTC, advance UTC and current advancing service/credential/grant/source/account/deletion versions and authority hash. The signature also binds the exact retained KeyId. Its fingerprint is SHA256 of the complete envelope, including the MAC.

Reuse `IGroupSourceKeyProvider` and its existing exact-scope secret resolver/enrollment. Derive a separate integrity key with HKDF-SHA256, a versioned scope salt and the fixed `aioffice-group-terminal-advance-integrity-v1` purpose, then HMAC the complete canonical metadata. Derived bytes are zeroed. The derivation excludes mutable authority versions so legitimate authority rotation does not invalidate earlier evidence. HKDF's application context separates derived keys for different uses. [RFC 5869](https://www.rfc-editor.org/rfc/rfc5869.html)

Enrollment must retain an immutable `(scope, KeyId) -> key material` mapping for every reachable advance. Missing keys or rebinding an ID refuse; there is no fallback to a current/global/company key and no automatic re-signing. This introduces no independent AI client, provider configuration or secret store. The source and brain ciphertext formats remain unchanged.

## Required SQL and caller implementation

1. Add a versioned expansion for immutable advance receipts. Restrictive scoped FKs bind the exact terminal interval and exact predecessor through/version/full-envelope fingerprint. Unique scoped version and predecessor constraints prevent forks. First version is one with After zero and every predecessor FK field explicitly NULL; later versions require every predecessor component NOT NULL, previous version plus one and After equal previous Through. Composite FK nullness and CHECK unknown values need explicit treatment. [SQL Server foreign keys](https://learn.microsoft.com/en-us/sql/relational-databases/tables/create-foreign-key-relationships?view=sql-server-ver17), [CHECK constraints](https://learn.microsoft.com/en-us/sql/relational-databases/tables/unique-constraints-and-check-constraints?view=sql-server-ver17)
2. Bind the mutable cursor to the exact signed leaf through/version/batch and signed advance UTC. Runtime may INSERT/SELECT advance receipts but must have no UPDATE/DELETE/ALTER/TAKE OWNERSHIP or writable advance columns. Keep the existing four writable cursor columns and immutable scoped identity restrictions.
3. Under fresh current Extract authorization, read bounded predecessor/cursor metadata. Resolve the retained predecessor read key and active write key outside SQL. In a new pinned Serializable/source-APPLOCK unit, reread those exact bytes, current cursor, enrollment/authority and the latest scoped advance. Unknown or forged newer rows refuse. An authentic old leaf is insufficient: cursor must equal the latest authenticated leaf, including its signed UTC. Never derive completion from MAX terminal sequence.
4. Reconstruct the target terminal's complete original immutable allocation/raw/cutoff/claim/work/effect/own-input graph and exact original dependency/terminal bytes using a distinct sealed historical type. Preserve original commit-within-acquisition lifetime. Do not fabricate a Current verdict, obsolete handle or old current clock, and do not regenerate today's mutable source/IT/glossary fingerprints as historical evidence. Recheck current Extract/source/account/service and effective SQL rights separately. Revocation/deletion continues to refuse.
5. Verify the predecessor signature/chain before signing. Advance only the exact next interval; a completed later interval cannot skip an earlier pending one. A bounded scanner repeats with explicit continuation beyond 100 intervals; every continuation begins from the authenticated latest leaf. Scheduled backlog, unscheduled committed work and coverage gaps remain distinct.
6. Atomically save the signed advance and cursor, with exact actual SQL readback and monotone UTC/version checks. Acquire the source lock before the effect savepoint. Roll back/detach both effects before any witness-only lease retirement. Preserve cancellation, session restoration, lost-reply replay with no extra advance/version, and clean transaction/tracker state.

The predecessor chain supplies an inductive trust anchor only when the future store enforces these rules before every Sign. A host holding a signing key can sign arbitrary shaped metadata with this primitive; signature validity alone is not original graph proof or current authority. Compromise of the source key itself is outside the protection against malformed SQL metadata. Historical signature verification does not release old source plaintext.

## Implemented primitive and verification scope

`GroupTerminalAdvanceIntegrity` encodes exactly version-one `AIOGFAD1` envelopes, 322–385 bytes including a 32-byte MAC. It validates scope/identities/ranges/versions/genesis-versus-successor shape, exact UTC ordering, positive authority versions, fixed nonzero terminal/authority hashes, finite ASCII KeyId and complete EOF. Input bounds are checked before allocation; returned metadata/envelopes are detached copies. Errors are fixed and inner-free. `PeekKeyId` is explicitly untrusted, exact-scope key selection; authentication still requires the full MAC.

38 new controls pass: an independent manual binary layout and RFC extract/expand computation, mutation of every carrier byte, failed unkeyed checksum forgery, cross-scope/same-key attacks, wrong/disposed keys, malformed metadata and frames, exact range/key/version bounds, immutable copies and retained-key rotation. These are real cryptographic computations over synthetic metadata; they are not SQL chain, authority, restart, key-await race, cursor, model or application acceptance. The active exact `b3c7dfb` CI predates this primitive and cannot qualify it. Full #278/#279/#233 and merge remain incomplete; real model evaluation stays **NOT_RUN_UNEVALUATED** through the existing AI Gateway.
