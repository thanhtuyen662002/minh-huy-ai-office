## Call order and durable recovery

`GroupOriginalModelChunkCoordinator` receives a closed original plan and one rebuilt model chunk. Its first effectful dependency is `ReadOriginalAsync` from the existing accepted-result store. Accepted output is parsed against the rebuilt exact context and sent to the final SQL effect writer. Recovery does not consult the retry budget, original-admission sidecar, current admission companion, provider configuration or present-day model release. Those older immutable results remain usable after a model is removed, subject to fresh source/history/claim/authority fences.

When no accepted output exists, the journal reads the original chunk's durable attempt budget under its existing current SQL unit. This read grants no execution authority. A waiting decision returns a UTC retry time for the later durable scanner. Exhaustion goes through `CommitExtractionFailureAsync`, whose final SQL transaction proves actual exhaustion again. There is no timer, delay, retry loop, caller-provided exhaustion flag or in-memory work ownership in this coordinator.

Only an available budget proceeds to the authenticated original sidecar, current preparation and atomic admitted start. A lost start reply, replayed nonce or newly unavailable budget never releases another provider call. A returned permit must belong to that exact preparation/context and must be newly started. The fixed journal's execution method performs the independent current SQL fences before and after the existing Gateway wait. A parsed response is durably protected and persisted **before** any note or no-work effect. Subsequent recovery uses that accepted output first.

Invalid output appends the existing bounded failure kind; only existing typed Gateway provider failures enter the transient/permanent classification. Local guard failures and cancellation cannot become provider failures or automatic attention. An expired response rereads the durable budget without appending an out-of-deadline failure. No failed write is returned as completed. Cancellation is checked across each dependency await; a final committed SQL transaction remains safely replayable if its reply is lost or the caller cancels afterward.
